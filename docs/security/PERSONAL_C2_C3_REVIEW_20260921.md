## C2 — key custody and restore

**C2-01, already implemented:** Per-store 32-byte HMAC seal key and externally supplied 32-byte AES-256-GCM archive key are distinct; reuse denied, fresh nonce per archive/rewrap. The completed encrypted archive carries the seal key *inside ciphertext*. New-file key rewrap preserves the old archive and does NOT rotate the store HMAC key. These properties require no new product feature.
**C2-02, owner workflow required BEFORE using real archive backup:** Keep the archive key in an owner-controlled encrypted vault or explicitly approved macOS Keychain item, separate from the archived data; maintain a recoverable second copy under owner control. Verify one offline restore into a newly created disposable root before retiring the old archive/key. Never pass key material via chat, MCP, CLI arguments, environment, stdout, repo or logs. Losing the sole archive key can make restore impossible. This is an *operator contract*, NOT an implemented Keychain integration or claim of real backup.
**C2-03, crash/durability boundary:** Native `renameatx_np(RENAME_EXCL|RENAME_NOFOLLOW_ANY)` and stage dev/ino checks refuse concurrent existing targets. Helper performs `fsync(destparent)`; source-parent durability and rename/power-loss reconciliation are not independently proven. Hash-checking the private helper file before spawning by pathname also is not a signed artifact or a same-UID TOCTOU proof. The source SHA-256 is `590806dc0ce2b293db85755a72934d8df28ad6c6ce44a389e79e8b5c8152542f`; binary hash must be computed for the actual release build, never inferred from source hash.
**C2-04, plaintext and cleanup:** Normal archive/decrypt staging now uses C1-1 fixed allowlisted non-recursive deletion and intent; raw backup/restore uses C1-2 owned scratch cleanup. Hostile same-UID parent/leaf races, post-intent crash reconciliation and transient plaintext exposure remain OPEN. Never claim this is a sandbox or unattended cleanup under hostile same-UID access.
**C2-05, remaining archive output window:** An interrupted archive write may leave a new incomplete `wx` destination before final parent sync; identify and authenticate the exact file before any cleanup or retry. Completed archive and successful restore can be distinguished from a cleanup failure. No blind rewrap, overwrite or old-key revocation.
**Decision for single-owner product:** Do not add global locks, automatic Keychain creation, a background rotation service, blanket escrow requirements or extra prompts to normal execution. Keep offline backup/restore OUT of MCP and Business candidate inventory until its owner key/recovery workflow is exercised; useful existing Personal file/process/memory MCP can be reviewed and accepted separately for a new private app once its *exposed* scope passes independent review and owner approval.
